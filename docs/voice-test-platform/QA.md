## 第十六轮 平台仅对接模块契约和启动方式

### R16-Q62 模块内部实现不成为平台分类

用户原话：

> 为啥会有外部接口和仓库+外部接口，这种不是说了是模块内部自行用代码实现吗，我们只对接模块和模块的启动方式，是本地启动还是docker启动，是否是外部则是他们内部代码自行决策

纠正：平台统一导入、启动和调用模块，不提供“外部接口”“仓库代码”“仓库 + 外部接口”能力来源枚举，也不提供固定外部协议、服务地址或服务版本表单。模块内部是否调用外部服务、引用代码或组合，由其代码自行决定。模块需要开放的业务配置由自己的参数 Schema 与前端组件定义，平台只验证、保存和传入这些参数。

运行要求仍由模块声明：后端语言不限，本地进程/Docker 为启动方式，平台通信保持 HTTP 管理/WebSocket 流式。仓库管理用于按声明准备代码依赖及固定版本，不用于给模块分类或猜测其内部调用路径。模块内部实际执行和服务身份仅按主动上报的 Trace 证据展示；本地停止不能代替内部停止证据。

本轮按既有 docs/demo 更新授权修正设计、QA、原型运行模型、导入表单、节点配置与快照，并同步逻辑和端到端测试，移除上一轮错误扩展的分类及连接字段。

## 第十七轮 启动方式优先与 Docker 仓库挂载

### R17-Q63 本地语言/入口与 Docker 镜像/挂载分别配置

用户原话：

> 选中了 docker 之后还需要运行入口吗， 是否应该是先是选择启动方式，然后对于docker只是把对应的仓库挂载到 docker 的某个目录下，然后对应本地进程则是让用户下拉选择后端语言，然后选择运行入口

结论：导入与流程节点先选择启动方式。Docker 不要求本地语言和运行入口，用户配置可直接启动的模块镜像，并按需选择仓库/固定版本与容器挂载目录；镜像提供环境和 ENTRYPOINT/CMD，平台不覆盖启动命令。仅挂载文件不会自动启动代码，实际执行需要验证镜像及模块就绪。镜像已有代码或无仓库要求时可以不挂载。

本地进程下拉选择语言/运行配置，再选择入口；仓库代码按固定版本解析，模块包自带代码可直接使用。语言下拉保留“其他 / 自定义”，不重新限制后端语言。解释型选择脚本，编译型选择构建后可运行产物；自定义运行方式和依赖/构建要求由模块声明。

切换方式保留各自草稿，版本与执行快照只记录生效分支。本轮按现有授权同步 docs、demo 与验证；真实进程、Docker 和仓库挂载仍属于后续执行器实现。
